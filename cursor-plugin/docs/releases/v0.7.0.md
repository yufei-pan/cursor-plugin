# Cursor plugin 0.7.0 (yufei-pan fork)

Fork of the upstream 0.6.6 release with the client-side admission budget and the
executor envelope cap removed.

## Removed client-side rejections

- The `conservative_utf8_bytes_v1` admission budget is no longer enforced. The
  plugin previously rejected any request whose input JSON exceeded 983,616
  bytes, plus per-message/tool/image overhead accounting, output reserves and
  8192-message / 256-tool caps. That heuristic assumed one conservative unit
  per byte (and >= 65,536 units per image) and rejected requests far below the
  models' real capacity. Requests now go to Cursor directly.
- The 4 MiB executor envelope cap was removed (also size-based, and easy to
  exceed with base64 images).
- The byte-based local output truncation driven by `max_tokens` /
  `max_completion_tokens` is no longer applied; upstream output is returned as
  Cursor produced it.

## What still applies

- Structural request validation (malformed payloads, bad roles, negative
  `max_tokens`, unsupported tool shapes) still returns HTTP 400.
- The 16 MiB per-attachment parser cap for file/image data remains.
- The 90-second no-progress transport watchdog remains (a Cursor-side stall
  surfaces as `cursor_progress_timeout`, HTTP 504).
- Session admission, checkpoint, replay and tool-loop behavior are unchanged.

`count_tokens` still reports `count_method: conservative_utf8_bytes_v1` with
`estimated: true`; the count is informational and never rejects a request.

## Compatibility

Same plugin ABI (version 1) and host integration as 0.6.6. Replacing the
plugin binary and restarting CLIProxyAPI is sufficient. Plugin store metadata
(`plugins.configs.cursor.store.version`) must match the installed binary's
version for the host to load it.

Verified on the live server: a 1,004,606-byte request completes in ~18s, a
4.03 MiB text request in ~31s, and a 6.45 MiB request containing a 5 MB PNG
image in ~8s.
